Масштаб один на всех слоях. |

## 2. Поднятые сервисы — и почему именно они

`docker ps` (у меня все контейнеры с префиксом `vk-` и свои тома `vk-minio-data`, `vk-pg-data`):

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO (`vk-minio`, образ `pgsty/silo`) | S3-совместимое объектное хранилище, сюда физически падают parquet/orc-файлы и metadata.json | S3-API — стандарт де-факто: тот же код и конфиги работали бы с AWS S3/Yandex Object Storage. Хранилище отделено от вычислений: можно поменять движок (я подключила второй — Spark), а данные останутся на месте. Официальные образы MinIO больше не раздаются (401), поэтому взяла свободный форк Silo — те же порты, переменные и консоль. |
| PostgreSQL 17 (`vk-pg`, порт **5433**) | БД, где Lakekeeper хранит метаданные каталога (warehouse, namespace, указатель на текущий metadata.json таблицы) | Надёжная транзакционная БД: каталог должен атомарно переключать «текущую версию» таблицы — это основа ACID в Iceberg. Postgres открытый и Lakekeeper поддерживает его из коробки. Порт 5432 на машине занят локальным Postgres, поэтому проброс 5433→5432 и `:5433` в `LAKEKEEPER__PG_DATABASE_URL_*`. |
| Lakekeeper (`vk-lakekeeper`) | Iceberg REST Catalog — каталог метаданных таблиц | REST-каталог — открытый стандарт Iceberg: к нему одинаково подключились и Trino, и Spark, без Hive Metastore (тяжёлый, Java + отдельная БД). Lakekeeper лёгкий (Rust, ~35 МБ RAM у меня), один контейнер, умеет несколько warehouse — у меня их 4: bronze/silver/gold/bench. |
| Trino 476 (`vk-trino`) | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Интерактивный MPP SQL-движок с хорошим Iceberg-коннектором (CTAS, MERGE/UPDATE/DELETE, time travel, `$files`/`$snapshots`, schema evolution, `rollback_to_snapshot`) и встроенным генератором `tpch` — данные не надо качать. По сравнению со Spark стартует мгновенно, на моём Q16 быстрее (§6.2). |
| Spark 3.5.3 (`vk-spark`, по запросу) | Второй движок поверх того же lakehouse (раздел 6.2) | Показывает главное свойство lakehouse: открытый формат — Spark прочитал таблицы, записанные Trino, через тот же каталог, ничего не экспортируя. |

Каталоги Trino: `bronze`, `silver`, `gold`, `bench` (Iceberg REST, каждый — свой warehouse и свой бакет) и `tpch` (генератор). `SHOW CATALOGS` → `bench, bronze, gold, silver, system, tpch`.

### Скрипты, которыми поднимала стек

Полностью — [`scripts/01_up_stack.sh`](scripts/01_up_stack.sh) и [`scripts/02_init_storage.sh`](scripts/02_init_storage.sh):

```bash
# MinIO — объектное хранилище (S3 API 9000, консоль 9001)
docker run -d --name vk-minio -p 9000:9000 -p 9001:9001 \
  -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=minioadmin \
  -v vk-minio-data:/data pgsty/silo:latest server /data --console-address ":9001"

# PostgreSQL — метаданные Lakekeeper (5432 занят локальным Postgres -> 5433)
docker run -d --name vk-pg -e POSTGRES_PASSWORD=postgres -p 5433:5432 \
  -v vk-pg-data:/var/lib/postgresql/data postgres:17

# Lakekeeper — миграции БД (один раз) и сам REST-каталог на 8181
PG_URL=postgresql://postgres:postgres@host.docker.internal:5433/postgres
docker run --rm -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' \
  -e LAKEKEEPER__PG_DATABASE_URL_READ=$PG_URL -e LAKEKEEPER__PG_DATABASE_URL_WRITE=$PG_URL \
  quay.io/lakekeeper/catalog:latest-main migrate
docker run -d --name vk-lakekeeper -p 8181:8181 -e 'LAKEKEEPER__PG_ENCRYPTION_KEY=This-is-NOT-Secure!' \
  -e LAKEKEEPER__PG_DATABASE_URL_READ=$PG_URL -e LAKEKEEPER__PG_DATABASE_URL_WRITE=$PG_URL \
  quay.io/lakekeeper/catalog:latest-main serve

# Trino — SQL-движок; монтирую папку каталогов и свой config.properties (лимит памяти запроса 4GB)
docker run -d --name vk-trino -p 8080:8080 \
  -v "$(pwd)/catalog:/etc/trino/catalog" \
  -v "$(pwd)/trino/config.properties:/etc/trino/config.properties" trinodb/trino:476

# бакеты bronze/silver/gold/bench (mc) + Terms of Use + 4 warehouse в Lakekeeper (REST API)
./scripts/02_init_storage.sh
```

## 4. Медальон — решения по каждому слою

Размеры — сумма `file_size_in_bytes` из `"<таблица>$files"`, формат/кодек — из `"$properties"`, партиционирование — из `SHOW CREATE TABLE` (скрипт [`scripts/layer_stats.py`](scripts/layer_stats.py), результат — [`results/layer_stats.csv`](results/layer_stats.csv)).

**Про «грязную» догрузку.** Данные `tpch` идеально чистые: проверкам качества в Silver было бы нечего ловить, и ELT был бы «для галочки». Поэтому в Bronze я сделала два батча: batch 1 — полная выгрузка `tpch.sf10`, batch 2 — специально испорченная догрузка (append, как и положено в Bronze, [`sql/11_bronze_dirty_batch.sql`](sql/11_bronze_dirty_batch.sql)): повторы ключей с пробелами по краям и `type` в нижнем регистре, NULL в ключах и в бренде, недопустимые `size` (0, −5, 77), отрицательный остаток, «сироты» в `partsupp` (ссылки на несуществующие детали и поставщиков). Критерий успеха — после Silver витрина Gold должна совпасть с эталоном.

Итог карантина ([`results/dq_rejects_summary.csv`](results/dq_rejects_summary.csv)): part 60, partsupp 64, supplier 5 строк — 129 строк в `silver.lakehouse.dq_rejects`.

**Два решения, о которых спрашивали:**

- **Где отсеивать поставщиков с жалобами — в Gold, а в Silver только флаг.** В Silver поставщик получает `has_complaints = comment LIKE '%Customer%Complaints%'` (ровно та же логика, что в эталоне), но **не удаляется**. Silver — общий очищенный слой «одна правда о поставщиках»; «исключить жалобщиков» — бизнес-правило конкретного отчёта Q16. Если удалить их в Silver, любой другой отчёт (например, «сколько у нас поставщиков» или «какие поставщики проблемные») получит неверные цифры. Флаг вычисляется один раз, а в Gold фильтр превращается в дешёвый `NOT supplier_has_complaints` вместо `NOT IN` с подзапросом и `LIKE` по тексту.
- **Разбор `type` на части — в Silver.** `type` в TPC-H — это три слова: класс (`STANDARD`, `MEDIUM`…), обработка (`POLISHED`, `PLATED`…), материал (`TIN`, `BRASS`…). Разложить его на `type_class`/`type_finish`/`type_material` — это нормализация, полезная любому потребителю (например, «детали из латуни»), а не фильтр одного отчёта, поэтому место ей в Silver. В Gold условие `type NOT LIKE 'MEDIUM POLISHED%'` стало `NOT (type_class = 'MEDIUM' AND type_finish = 'POLISHED')` — читается понятнее и не зависит от шаблона строки. Сам исходный `part_type` я тоже оставила: он нужен в выводе витрины.

**Нормализация типов и имён:** колонки переименованы в понятный snake_case (`partkey` → `part_key`, `suppkey` → `supplier_key`, `availqty` → `available_qty`, `acctbal` → `account_balance`…); деньги `double` → `decimal(15,2)` (точная арифметика вместо плавающей точки); **обогащение:** `brand_mfgr_no`/`brand_no` из `Brand#MN`, части `type`, флаг `has_complaints`, `_processed_at`.

## 5. Тесты производительности

**Как мерила** ([`bench/run_bench.py`](bench/run_bench.py)): три Bronze-таблицы моего запроса (вместе с грязным батчем) скопированы CTAS-ом в каталог `bench` в 8 вариантах: PARQUET/ORC × NONE/SNAPPY/GZIP/ZSTD (кодек — `SET SESSION bench.compression_codec`, проверен в `$properties`: для ORC GZIP записался как `zlib`, NONE в Parquet — как `uncompressed`).

- **Размер** — сумма `$files` по трём таблицам.
- **Запись** — CTAS всех трёх таблиц, два полных раунда записи → медиана и разброс.
- **Q16 cold** — перед каждым холодным прогоном: сброс page cache виртуальной машины Docker (`echo 3 > /proc/sys/vm/drop_caches`), `docker restart vk-minio vk-trino`, ожидание активного узла. Просто рестарта MinIO мало — файлы остались бы в кэше ОС виртуалки.
- **Q16 warm** — 3 прогона сразу после холодного.
- Всё это 3 раунда, в каждом раунде варианты идут по кругу (чтобы «дрейф» машины не лёг на один вариант). Итого на вариант: 3 cold + 9 warm. Время — `exec` из `system.runtime.queries` (чистое время запроса в Trino).

**Выводы (только по цифрам):**

1. **Размер — разница огромная и однозначная.** Без сжатия 1.23 ГБ, SNAPPY в ~2.7 раза меньше, GZIP/ZSTD — в ~4 раза. Почти весь объём — это `partsupp` (1089 МБ без сжатия → 245–275 МБ), а в нём — текстовая колонка `comment`, которая отлично жмётся. Parquet и ORC на одном кодеке почти равны (±1–5%): у ORC чуть меньше с SNAPPY/ZSTD, у Parquet — с GZIP.
2. **Запись — заметно медленнее только Parquet GZIP** (83–94 с против 42–68 с у остальных Parquet). У ORC разброс большой (ORC SNAPPY 58–85 с), и NONE не оказался самым быстрым: видимо, запись упирается не только в CPU на сжатие, но и в ввод-вывод в MinIO внутри одной виртуалки и в память Trino (контейнер во время записи занимал 5.8–6.5 ГБ из 7.7 ГБ по `docker stats`) — точную причину я не доказала. Поэтому кроме «GZIP в Parquet медленный» других выводов по записи я не делаю — разброс между раундами до 25 с.
3. **Время Q16 — разница в пределах шума.** Диапазоны cold у всех 8 вариантов пересекаются (3.8–8.0 с), warm тоже (1.1–4.5 с). По медианам warm сжатые варианты чуть быстрее NONE (1.5–2.0 с против 2.4 с), но разброс внутри одного варианта больше, чем разница между вариантами — честно сказать «X быстрее Y» я не могу. **Почему так:** Q16 — колоночный запрос. Через `EXPLAIN ANALYZE` ([`results/bench_physical_input.txt`](results/bench_physical_input.txt)) видно, что из `partsupp` в 1089 МБ (Parquet NONE) физически прочитано всего 78.5 МБ, а из ZSTD — 19 МБ: читаются только `partkey` и `suppkey`, тяжёлый `comment` вообще не трогается. Данных для чтения мало, поэтому на время запроса больше влияют джойн, `count(DISTINCT)` и накладные расходы, чем кодек.
4. **Cold vs warm:** холодный прогон в 2–3.5 раза медленнее тёплого (≈4.5–5.7 с против ≈1.5–2.4 с) — это кэш страниц ОС и кэш метаданных Iceberg в Trino. Без сброса кэша «холодные» цифры были бы враньём: первая попытка с одним лишь рестартом MinIO давала бы уже прогретые файлы.
5. **Что выбрала:** PARQUET + ZSTD для всех слоёв. По размеру — почти как GZIP, по записи — как SNAPPY/NONE, по чтению — разницы нет. ORC+ZSTD по цифрам такой же хороший, но Parquet я взяла из-за экосистемы: его одинаково хорошо читают Trino, Spark, DuckDB, pandas, BI-инструменты. GZIP имеет смысл только для холодного архива, который пишется один раз и почти не читается; SNAPPY — когда важна скорость записи потока, а место дешёвое.

**Бонус 1 — Gold-запрос в 10 потоков** ([`bench/run_concurrency.sh`](bench/run_concurrency.sh), [`results/concurrency_gold_q16.csv`](results/concurrency_gold_q16.csv)): одиночный запрос (SELECT витрины из `silver.part_supplier`) — 2.52 / 2.76 / 2.68 с. 10 копий одновременно — 113.8 / 87.0 / 22.3 с на пачку. Это хуже, чем 10 одиночных подряд (~26 с), то есть система перегружена. Причина видна в логах: Trino съел почти всю память Docker, начались долгие остановки сборки мусора (пауза 6.7 с, heap 6.45 ГБ → 1.11 ГБ), а после третьей пачки ядро виртуалки убило контейнер Trino (`OOMKilled=true`, код 137). Вывод: на 7.7 ГБ для всего стека параллельность 10 этот запрос не тянет — пропускная способность не растёт, а падает. Лечится меньшим heap (`-Xmx`), очередью через resource groups или просто большей памятью. Конфигурацию я менять не стала, чтобы основной бенчмарк остался на тех же настройках, и просто перезапустила Trino.

**Бонус 2 — Trino vs Spark** на одной и той же таблице `bench` parquet_zstd, по 4 прогона подряд после сброса кэша ([`results/engine_compare_q16.csv`](results/engine_compare_q16.csv)):

| Движок | прогон 1 (холодный) | 2 | 3 | 4 | Что меряла |
|---|---|---|---|---|---|
| Trino 476 | 5.62 с | 3.72 с | 2.95 с | 1.80 с | exec из `system.runtime.queries` |
| Spark 3.5.3 (local[*], driver 4g) | 13.61 с | 6.72 с | 3.33 с | 5.04 с | `Time taken` (без ~15 с старта JVM) |

Оба вернули 27 878 строк. На моём объёме Trino быстрее в 1.5–2.5 раза и стабильнее; у Spark первый запрос платит за инициализацию каталога и JIT, и время скачет. Spark выигрывал бы на больших пакетных ETL и на кластере, а не на интерактивном запросе на одном ноутбуке. Для честности сравнения во время работы Spark я останавливала Trino (иначе не хватало памяти).

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ  |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная БД хранит данные внутри себя, в своём формате, и масштабируется вместе с сервером: место и вычисления покупаются вместе и дорого. Lakehouse разделяет **хранение** (дешёвое объектное хранилище, S3/MinIO, открытые файлы Parquet) и **вычисления** (Trino, Spark — любые, можно несколько сразу). При этом табличный формат Iceberg добавляет то, чего не было у «просто озера файлов»: транзакции (ACID через атомарную смену metadata.json в каталоге), схему и её эволюцию, снапшоты и time travel, статистику для оптимизатора. У меня это видно на практике: одни и те же файлы читали и Trino, и Spark через один Lakekeeper; за счёт колоночного формата Q16 прочитал из 1.1 ГБ таблицы всего 19–79 МБ; сжатие уменьшило хранение в 4 раза; после «аварии» таблицу удалось восстановить из снапшота. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | На копии `silver.lakehouse.part` (2 млн строк, 4 файла) я сделала ([`results/schema_evolution_log.md`](results/schema_evolution_log.md)): **ADD COLUMN** `price_band` → у всех 2 000 000 старых строк `NULL`, новая вставленная строка — `'HIGH'`; **RENAME** `part_comment` → `comment_text` — старые данные сразу читаются под новым именем; **расширение типа** `brand_no` `integer → bigint` и `retail_price` `decimal(15,2) → decimal(18,2)` — прошли; **сужение** `bigint → integer` Iceberg запретил: `Cannot change column type: brand_no: long -> int`. **Файлы не переписывались:** было 4 файла, стало 5 (пятый — от моего INSERT), и все 4 старых файла на месте (EXCEPT = 0). ALTER-ы не создали ни одного снапшота (их 2: CTAS и INSERT), но каждый дал новую версию metadata.json (8 версий). **По ID:** в metadata.json ([`results/schema_evolution_metadata.json`](results/schema_evolution_metadata.json)) видно 5 версий схемы: schema 1 — добавлено поле id 18 `price_band`; schema 2 — у поля id 14 сменилось только имя; schema 3 — у id 6 тип `int → long`; schema 4 — у id 13 `decimal(15,2) → decimal(18,2)`. Parquet-файлы хранят колонки по field-id, поэтому переименование ничего не ломает, а новое поле с id 18 в старых файлах просто отсутствует → NULL. |
| Пример скрипта восстановления данных из снапшота (time travel) | Полный лог — [`results/time_travel_log.md`](results/time_travel_log.md), скрипт — [`scripts/run_time_travel.py`](scripts/run_time_travel.py). На копии `silver.lakehouse.supplier`: **авария 1** — `DELETE FROM supplier_tt WHERE nation_key = 7` (пропали 4 049 поставщиков; в `$snapshots` видна операция `delete` с `added-position-deletes = 4049` — Trino не переписал файл, а дописал delete-файл). `FOR VERSION AS OF <v1>` и `FOR TIMESTAMP AS OF TIMESTAMP '...'` показывают 100 000 строк, из них 4 049 с nation 7. **Точечное восстановление:** `INSERT INTO supplier_tt SELECT * FROM supplier_tt FOR VERSION AS OF <v1> WHERE nation_key = 7` → 100 000 строк, разница с v1 в обе стороны = 0. **Авария 2** — `UPDATE supplier_tt SET has_complaints = true` без WHERE (100 000 «жалобщиков» вместо 56). **Откат целиком:** `ALTER TABLE silver.lakehouse.supplier_tt EXECUTE rollback_to_snapshot(<v3>)` — в Trino 476 работает: снова 56, расхождение с исходным Silver = 0 в обе стороны; в `$history` снапшот с кривым UPDATE остался, но `is_current_ancestor = false`. |

```sql
-- ядро сценария (id снапшотов берутся из $snapshots)
SELECT snapshot_id, committed_at, operation FROM silver.lakehouse."supplier_tt$snapshots" ORDER BY committed_at;
SELECT count(*) FROM silver.lakehouse.supplier_tt FOR VERSION AS OF 2499175251857534081;
SELECT count(*) FROM silver.lakehouse.supplier_tt FOR TIMESTAMP AS OF TIMESTAMP '2026-10-17 11:15:55.660 UTC';
-- точечно: вернуть только потерянные строки
INSERT INTO silver.lakehouse.supplier_tt
SELECT * FROM silver.lakehouse.supplier_tt FOR VERSION AS OF 2499175251857534081 WHERE nation_key = 7;
-- целиком: откатить таблицу на снапшот
ALTER TABLE silver.lakehouse.supplier_tt EXECUTE rollback_to_snapshot(6496036606520100153);
```

## 7. Выводы

Медальон — это не три копии одних и тех же данных, а три ответственности: Bronze хранит всё как пришло и даёт возможность перезалить и разобраться, Silver — единственное место, где данные проверяются и чистятся (у меня он поймал все подброшенные дефекты и ещё 3 091 настоящий пробел в адресах), а Gold — маленький готовый ответ, который я сверила с эталоном до нуля расхождений. Бизнес-правила одного отчёта (исключить жалобщиков) я держу в Gold, а общие преобразования (разбор `type`, флаг) — в Silver, чтобы Silver подходил любым отчётам. По хранению главный эффект дало сжатие (ZSTD/GZIP в 4 раза меньше NONE), а на скорость моего Q16 кодек почти не влияет, потому что колоночный формат читает только нужные 2 колонки из 5 — честно: разница по времени в пределах шума. Поэтому PARQUET + ZSTD — лучший компромисс для моей задачи: почти минимальный размер без медленной записи GZIP и с лучшей совместимостью. Отдельно поняла, что на ноутбуке узкое место — память: мне пришлось поднять лимит памяти запроса, а 10 параллельных запросов вообще уронили Trino.
